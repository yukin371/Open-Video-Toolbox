# v1.0 到后续版本功能规划卡

最后更新：2026-10-14

## 目的

这张卡把当前功能矩阵、压缩工作流和后续常用视频能力放到同一个版本规划中。它用于决定“先做什么、暂缓什么、什么不属于产品边界”。

当前主要方向是：**兼顾压缩分享与内容生产的 CLI 工作流**。核心价值是让个人创作者可以用稳定预设快速得到可分享文件，也可以把字幕、音频、素材和批量任务接入可审计的生产流程。

## 产品边界

### 正式交付面

- `OpenVideoToolbox.Core`：媒体模型、预设、命令构建、外部工具执行、计划模型和日志上下文。
- `OpenVideoToolbox.Cli`：参数、命令编排、结构化输出、退出码和可重放工作流。
- `OpenVideoToolbox.Desktop`：继续在 `ui` 分支独立开发，不作为 `v1.0` 发布阻塞条件；它只能消费 Core/CLI 已验证的能力。

### 用户承诺

v1.0 应让用户能够完成以下两条主路径：

1. **压缩分享**：探测素材，选择内置或自定义预设，执行转码，比较压缩前后大小，并在原目录生成带后缀的输出或写入指定路径。
2. **内容生产**：生成并维护 `edit.json`，接入字幕、配音、BGM 和 supporting signals，预览并渲染单个或批量任务。

v1.0 不承诺专业 NLE、复杂时间线、专业调色、复杂转场、角色动画或仓库内 AI provider。

## 版本分层

### v1.0 正式范围

下列能力已经存在或属于当前发布主线，继续作为 v1.0 的正式承诺面：

| 能力组 | 当前能力 | 用户结果 | 主要 owner | v1.0 验收口径 |
| --- | --- | --- | --- | --- |
| 依赖与探测 | `doctor`、`probe` | 知道工具是否可用，获得规范化媒体信息 | `Core.Media` / `Core.Execution` + `Cli` | required / optional 依赖区分清晰；JSON 与退出码稳定 |
| 传统转码 | `plan`、`run`、内置压缩预设、自定义预设 | 以可预览、可重放的方式完成压缩 | `Core.Presets` / `Core.Execution` | 命令预览与执行一致；保留完整外部工具日志 |
| 压缩输出 | 大小对比、原目录默认输出、后缀命名、显式输出路径与名称 | 不覆盖源文件，容易找到压缩结果 | `Core.Execution` + `Cli` | 默认类似 `video01_x264.ext`；输出路径可显式覆盖；结果包含前后大小 |
| 基础媒体处理 | `cut`、`concat`、`extract-audio` | 完成常见裁切、拼接和提音轨 | `Core.Execution` | 成功、失败和产物路径均结构化 |
| 计划与模板 | `templates`、`init-plan`、`scaffold-template`、`validate-plan` | 从模板快速起草可编辑计划 | `Core.Editing` + `Cli` | 生成的计划可检查；模板 guide / commands 与实际入口一致 |
| 计划维护 | `inspect-plan`、`replace-plan-material`、`attach-plan-material`、`bind-voice-track` | 替换和接回字幕、音频、节拍等外部产物 | `Core.Editing` | 文件检查、相对路径和后置校验语义稳定 |
| 渲染与混音 | `render`、`mix-audio` 及 preview | 在执行前审查副作用，输出视频或混音 | `Core.Execution` | preview 与执行使用同一命令语义；音频轨真实参与渲染 |
| 批量工作流 | `scaffold-template-batch`、`render-batch` | 批量准备、预览和渲染任务 | `Cli` 编排 + `Core` 执行 | 固定 `summary.json`、`results/<id>.json` 与 `0/2/1` 退出码 |
| 信号与字幕 | `audio-analyze`、`audio-gain`、`audio-normalize`、`transcribe`、`subtitle`、`detect-silence`、`beat-track`、`separate-audio` | 为内容生产提供可复用的音频、字幕和节奏文件 | 对应 `Core` 子模块 | 外部依赖缺失时错误可诊断；可选能力不阻塞核心发布 |
| 发布与编排 | single-file release、`--json-out`、结构化 envelope | 脚本和外部 AI 可稳定调用 | `Cli` | stdout 与 `--json-out` 语义一致；失败保留错误上下文 |

### v1.0 尾部：已交付的高性价比能力

这些功能服务于压缩分享和内容生产两个方向，已在 v1.0 主闭环稳定后完成实现、测试和验收，现属于 README 与命令参考中的正式能力。后续新增能力应进入 v1.1 候选区，不再把本节功能视为未交付候选。

| 优先级 | 功能卡 | 用户需求与常用场景 | 竞争价值 | 难度 | owner / 依赖 | v1.0 尾部验收 |
| --- | --- | --- | --- | --- | --- | --- |
| P0 | 竖屏 / 方形适配 `--fit` | 为短视频平台输出 `9:16`、`1:1`、`16:9`，避免用户手写滤镜 | 高；覆盖抖音、小红书、Reels 等高频发布场景 | 低 | `Core.Presets` / `Core.Execution`；依赖 `pad` 与 preset schema | 已实现：输出画幅和 SAR 正确；不裁掉主体；命令测试通过 |
| P0 | 缩放 / 分辨率 `--resolution` | 快速在 480p、720p、1080p 之间选择，替代当前固定 720p 路径 | 高；压缩和分享直接相关 | 低 | `Core.Presets`；与 `--fit` 共用尺寸模型 | 已实现：支持预设和显式尺寸；宽高比策略明确；未改变现有 preset ID |
| P1 | 抽帧 / 缩略图 `extract-frame` | 封面、预览图、外部 AI 关键帧，可按时间点、数量或间隔生成 | 高；使用频率高，几乎不增加编辑复杂度 | 低 | `Core.Execution` + `Cli` | 已实现：单点、多点、固定间隔和批量输出均有结构化结果；输出不覆盖输入 |
| P1 | 水印 `--watermark` | 发布前叠加 logo，支持九宫格位置、边距和透明度 | 高；满足品牌发布的常见最后一步 | 低 | `Core.Execution`；依赖 `overlay` 参数模型 | 已实现：图片路径、位置、边距、透明度可审计；预览与执行一致 |
| P1 | 字幕样式参数 | 调整字体、字号、颜色、描边和底部边距，而不是只能使用默认样式 | 中高；能明显改善成片可用性 | 低 | `Core.Subtitles` + `Core.Execution` | 已实现：使用稳定字段映射到 ASS/渲染参数；不暴露任意 FFmpeg 字符串 |
| P2 | `doctor` 硬件编码器探测 | 知道本机是否可用 NVENC、QSV 等，避免用户盲试 | 高；为后续硬件编码降低决策成本 | 低 | `Core.Execution` + `Cli` | 已实现：`ffmpeg -encoders` 结果可解释；可用 `--test-hardware-encoder` 做显式极小试编码；不静默更换编码器 |

`--fit` 和 `--resolution` 应放在同一轮设计中，统一尺寸、像素宽高比、补边颜色和输出命名模型，避免形成两个互不兼容的参数体系。

### v1.1：验证后再扩大能力面

| 功能 | 解决的问题 | 为什么放到 v1.1 | 前置条件 |
| --- | --- | --- | --- |
| 目录批量压缩与安全替换 `compress-batch` | 磁盘空间不足时递归处理旧视频，只在结果变小时替换原文件 | 会引入目录遍历、逐项继续、原地替换、临时空间和汇总报告语义；必须先把数据安全边界做成独立命令 | `Core.Execution` 批处理 owner；支持扩展名筛选、预览、临时文件清理、原子替换和 `summary.json`；默认不修改源文件，`--replace` 显式启用 |
| NVENC / QSV / VideoToolbox 预设 | 利用硬件降低编码时间 | 各机器驱动和编码器行为不同，兼容性和回退语义需要真实样本 | `doctor` 探测稳定；明确“不可用即报错”或显式用户选择，不静默回退 |
| `--target-size` 两遍编码 | 平台上传大小上限 | 会引入两遍执行、临时文件、失败恢复和 batch 汇总语义 | 固定 `ExecutionResult`、临时产物清理和取消策略 |
| 更强批处理与恢复 | 大批量生产时减少人工重跑 | 涉及任务状态、断点、重试和持久化，影响面明显 | 先明确任务记录 owner 与持久化形态 |
| 发布平台预设包 | 让常见平台输出更少手工配置 | 平台规则经常变化，不宜在 v1.0 末尾快速堆积 | 尺寸、码率、音频和命名模型稳定；预设版本可追踪 |
| 字幕样式进阶 | 多语言、主题和模板化字幕 | 依赖 v1.0 字幕字段和字体发现边界稳定 | 样式 schema、字体缺失错误和跨平台渲染已验证 |

#### 真实工作场景与功能需求

| 场景 | 使用者要解决的问题 | 必须提供的能力 |
| --- | --- | --- |
| 硬盘告急，素材仍需保留 | 旧项目、录屏、手机导出和直播录像占满空间，不能靠人工逐个处理 | 递归遍历、视频扩展名筛选、按目录/文件名排除、单文件串行处理和预览清单 |
| 混合素材库 | 同一目录包含已压缩视频、原始相机素材、损坏文件和非视频文件 | `probe` 信息、编码器/容器筛选、跳过规则、不可读文件单独报告，不因一个坏文件中止全批次 |
| 压缩后原地释放空间 | 用户不需要第二份副本，但不能因为新文件损坏而丢失旧文件 | 临时文件、输出可解码验证、结果更小检查、显式 `--replace`、提交失败回滚 |
| 长时间无人值守 | 夜间或工作日运行，硬件错误、断电、磁盘不足都可能发生 | 每项状态、完整 stdout/stderr、退出码、错误分类、可恢复的 `summary.json` 和断点续跑 |
| 重复运行 | 第一次中断后再次运行不能反复压缩或覆盖仍在处理的文件 | 输入指纹、已处理记录、临时文件清理、幂等跳过和明确的重试策略 |
| 归档合规与人工复核 | 文件名、修改时间、字幕旁车文件和目录结构可能有后续用途 | 保留相对路径与文件名，提供时间/属性保留选项，替换前后记录旧文件与新文件信息 |

#### 批量替换的安全契约

1. 默认只生成预览和报告；只有显式 `--replace` 才允许修改源文件。
2. 每个输入先在同目录或指定临时目录生成唯一临时输出；FFmpeg 非零退出、超时、取消、磁盘不足或硬件错误都只能进入失败状态，不能触碰源文件。
3. 提交前至少完成结构验证和解码验证：`ffprobe` 确认容器、视频流、音频流和时长可读，再用 FFmpeg 解码验证；默认应覆盖完整文件，抽样验证只能作为明确的速度选项。
4. 只有新文件可解码、包含预期媒体流、大小严格小于源文件且所有报告已写入时，才进入替换阶段；不变小或变大的结果一律跳过并删除临时文件。
5. 替换阶段先保留可恢复的旧文件或等价回滚记录，再完成同目录提交；提交或回滚失败必须在结果中标为 `recoveryRequired`，不能报告为成功。
6. 硬件编码器错误不得静默切换编码器。可选的软件编码 fallback 必须由用户显式指定，并在报告中记录原始失败和 fallback 结果。
7. 批次采用逐项继续策略：单项状态至少区分 `compressed`、`skippedLarger`、`skippedInvalid`、`failed`、`replaced` 和 `recoveryRequired`；批次退出码沿用 `0` 全部成功、`2` 部分失败或有跳过、`1` manifest/参数错误。
8. 报告至少记录源路径、输入指纹、输入/输出大小、节省字节数、预设、编码器、验证结果、进程退出码、stderr 摘要、替换时间和最终状态；完整日志仍保留在外部工具执行结果中。

当前 v1.0 的 `run` 已具备临时输出、较大结果拒绝、失败清理和提交回滚基础，但没有目录遍历、批次恢复或替换前完整解码验证，因此不能把单文件 `run` 加脚本循环当作该功能的正式实现。

### v2：明确延后或暂不做

以下能力与产品长期方向有关，但会显著改变时间线、渲染或交互模型，不纳入 v1.0 / v1.1 的默认承诺：

- 转场编排、多轨复杂时间线、画中画和关键帧系统。
- 专业调色、LUT、复杂特效和需要连续预览的交互编辑。
- 角色动画、Live2D、骨骼绑定和表情驱动。
- 内置 AI provider、远程模型调用或不可审计的黑盒编排。
- GIF 导出。需求存在，但当前性价比低于竖屏、抽帧、水印和字幕样式。

这些方向只有在 CLI/Core 契约长期稳定、且有明确用户样本证明需求后，才进入独立的 v2 准入卡。

## 优先级判断规则

每个候选功能进入实施前，至少回答以下问题：

1. 是否对应个人创作者每周都会遇到的真实场景？
2. 是否能复用现有 `Core` owner、执行模型和结构化输出？
3. 是否能在不改变已发布命令语义的情况下增加能力？
4. 是否有明确的竞品差距或可感知的使用成本下降？
5. 是否能写出成功、失败、输出产物和跨平台限制的验收标准？

评分建议使用 1 到 5 分：用户频率、竞争价值、实现可控性各占一项；总分相同时，优先选择影响范围小、能复用现有执行路径的功能。

## v1.0 放行门槛

在决定创建 `1.0.0` tag 前，应满足：

- `probe -> plan -> run` 在受支持环境中稳定通过。
- `templates -> init/scaffold -> validate -> render` 至少有 manual 或 seeded clips 的可复现路径。
- `inspect -> attach/replace/bind -> render` 能维护字幕和音频绑定，且实际音频链路生效。
- `scaffold-template-batch -> render-batch` 稳定写出批量摘要和单项结果。
- 压缩工作流能展示前后大小，默认输出不覆盖源文件，显式输出路径和名称可用。
- 关键命令的成功、失败、preview、`--json-out` 和退出码契约有测试保护。
- `doctor` 能清晰区分 required 与 optional 依赖；缺少 optional 工具不会伪装成核心故障。
- 发布文档明确区分 v1.0 正式范围、附带能力和 Desktop / v2 延后范围。

## 下一轮执行顺序

1. v1.0 的 Core + CLI 功能、测试、真实媒体 smoke 和文档已完成；保留发布签发前的 maintainer 复核。
2. v1.1 优先设计并实现目录批量压缩与安全替换，先完成预览、单项大小保护、临时文件清理和汇总报告，再开放 `--replace`。
3. v1.1 再依据 `doctor` 的真实硬件探测结果评估 NVENC / QSV / VideoToolbox 预设，并评估 `--target-size`、任务恢复和平台预设包；这些能力不回写为 v1.0 承诺。
